C-001 Supabase Queries Silently Fail — No Error Handling Critical Data Handling
app/page.tsx — Lines ~80-200
What happens: Every Supabase database call on the main dashboard grabs { data } but completely ignores the { error } response. If any query fails (network drops, auth token expires, table gets renamed), data comes back as null.

Why it's bad: The code then tries to run .filter() or .map() on null, which instantly crashes the entire page with a "Cannot read properties of null" TypeError. The user sees a blank white screen with no explanation of what went wrong.
For the user

If your internet is slow, disconnects for even a second, or the server has a hiccup, the entire dashboard goes completely blank — just a white screen with nothing on it. There's no error message, no "try again" button, nothing. You'd have to refresh the page and hope it works this time.

C-002 Timezone Bug — Tasks & Habits Appear on Wrong Day Critical Logic
app/page.tsx, app/habits/page.tsx — Multiple locations
What happens: The code uses new Date().toISOString().split('T')[0] to figure out "today's date". But toISOString() converts to UTC time, not local time.

Why it's bad: For users in India (IST = UTC+5:30), after 5:30 PM local time, toISOString() returns tomorrow's date. This means:
  • Tasks due "today" disappear from the dashboard in the evening
  • Habit completions logged in the evening get saved to the wrong day
  • The "today" filter shows tomorrow's items instead
For the user

After around 5:30 PM every evening, your tasks for today just disappear from the dashboard. If you mark a habit as done at 9 PM, it gets counted as tomorrow's completion — so today still shows as missed. Your habit streaks will break even though you actually did the work.

// ❌ Gives UTC date — WRONG after 5:30 PM IST const today = new Date().toISOString().split('T')[0]; // ✅ Use local date instead const today = new Date().toLocaleDateString('en-CA'); // returns YYYY-MM-DD in local tz
C-003 Habit Logs Can Be Duplicated — Race Condition on Double-Tap Critical Async / Logic
app/habits/page.tsx — Lines ~120-160
What happens: When a user taps the "complete habit" toggle, the code checks if a log exists for today and then inserts or deletes accordingly. But there's no debouncing or loading lock on the button.

Why it's bad: If a user quickly double-taps the toggle (very common on mobile), two insert requests fire before either finishes. Both see "no existing log" and both insert a new row, creating duplicate log entries. This corrupts the habit streak data and scoring calculations.

If you quickly tap the "done" button twice (which is really easy to do on a phone), your habit gets logged twice for the same day. This messes up your streaks and scores. You might also find it impossible to "un-check" the habit later because only one of the two entries gets removed.

H-001 Sequential Database Queries — Page Loads 5-10× Slower Than Needed High Performance
app/page.tsx — Lines ~80-200
What happens: The main dashboard makes 10+ Supabase queries one after another using await in sequence. Each query waits for the previous one to finish before starting.

Why it's bad: If each query takes ~200ms, the total load time is ~2 seconds (10 × 200ms). Using Promise.all() would run them all at once, bringing the load time down to just ~200ms total. Users are staring at a loading spinner 5-10× longer than necessary.
For the user

Every time you open the app or go to the dashboard, you wait 2-3 seconds staring at a loading spinner when it could load almost instantly. This happens every single time. If your internet is slow, it could be 5+ seconds of waiting.

H-002 65KB Single Component — Entire Dashboard in One File High Performance
app/page.tsx — 1700+ lines
What happens: The main page is a single 65KB file containing all dashboard logic, UI, state, and data fetching. There's no code splitting or lazy loading.

Why it's bad: The browser has to download, parse, and execute this entire file before showing anything — even sections the user hasn't scrolled to. On mobile devices with slower processors, this causes a noticeable delay before the page becomes interactive.
For the user

The app takes extra time to start up on your phone, and you might notice the page loads but buttons don't respond for a second or two. Older phones or phones with lots of apps open will feel this delay even more.

H-003 Trip Distance Can Be Negative — No Start/End Validation High Logic

Why it's bad: If numbers are entered wrong, the trip shows a negative distance (e.g., "-150 km"). This negative value then cascades into fuel efficiency and total distance statistics, making them all incorrect.
For the user

If you accidentally swap the start and end odometer numbers, the app shows you drove "-150 km" — a negative distance. It doesn't warn you about the mistake, and this wrong number messes up your total distance and fuel reports going forward.

H-004 15-20+ useState Calls — Unmanageable State, Excessive Re-renders High State / Performance
app/page.tsx — Lines ~30-70

Why it's bad: Each setState triggers a separate re-render of the entire component (which is already 65KB). For the user

When the dashboard loads, you'll notice elements flickering, content jumping around, and the page feeling "janky". Cards and numbers might briefly show wrong values before settling. It feels unpolished and sluggish, like the app is struggling to keep up.
